# 22 Design Agent API

**Status:** Complete

Set up durable design generation delivery with Supabase Queues and a Supabase Edge Function worker.
This unit handles enqueueing, worker invocation, recovery, and persistent run tracking. No AI logic yet.

## Implementation

1. Add task run tracking.

   Create a `task_runs` table in Supabase with:
   - `id` (uuid primary key generated by PostgreSQL, also the client visible run ID)
   - `project_id` (uuid foreign key to `projects`)
   - `user_id` (uuid foreign key to `auth.users`)
   - `kind` (`design` or `spec`)
   - `status` (`queued`, `running`, `retrying`, `completed`, or `failed`)
   - `attempt_count` (small integer, default 0)
   - `error_message` (nullable sanitized text)
   - `created_at`, `updated_at`, `started_at`, and `completed_at` timestamps

   Add database constraints for allowed kinds, statuses, nonnegative attempt count, and valid terminal timestamps.

   Add:
   - separate indexes on `project_id` and `user_id` because both are foreign keys
   - a partial unique index on `project_id` where status is `queued`, `running`, or `retrying`, enforcing one active AI run per project
   - RLS with a `SELECT` policy that reuses the existing project owner or collaborator access check
   - explicit `SELECT` grant to `authenticated`
   - explicit revocation of browser `INSERT`, `UPDATE`, and `DELETE` privileges
   - `task_runs` to the `supabase_realtime` publication

   Only trusted server and Edge Function clients create or update task runs.

2. Add the durable queue.

   Enable `pgmq` and create one basic queue named `ai-generation`. Do not use an unlogged queue.

   Expose the `pgmq_public` Queue API only so trusted server clients can call it. Grant the required queue operations to the privileged server role. Do not grant queue access to `anon` or `authenticated`, and keep RLS enabled on the queue table.

3. Add transactional enqueueing.

   Create a database function callable only by the privileged server role. In one transaction it should:
   - create the queued `task_runs` row
   - send one queue message containing the run ID, kind, trusted project and user IDs, and validated input
   - return the run ID

   Use `SECURITY INVOKER`. Revoke execution from `PUBLIC`, `anon`, and `authenticated`.

4. Add the design route.

   Create `POST /api/ai/design`.
   This route should:
   - accept and validate `prompt` and `roomId`
   - authenticate the current user
   - resolve project access from `roomId`; do not trust a client supplied project ID
   - call the transactional enqueue function through a server only secret client
   - return HTTP 409 when the project already has an active AI run
   - invoke `ai-worker` as a best effort fast path after the queue transaction commits
   - still return `{ runId }` with HTTP 202 if the fast path invocation fails, because Cron will recover the queued message

5. Add the queue worker.

   Create `supabase/functions/ai-worker/index.ts` and pin dependencies in `supabase/functions/deno.json`.

   Configure the function with `verify_jwt = false`, then authenticate inside the handler with `withSupabase({ auth: "secret:automations" })`. The named automation secret must exist only in the Next.js server environment, Edge Function environment, and Supabase Vault.

   The worker should:
   - read one message from `ai-generation`
   - use a visibility timeout longer than the deployment tier maximum processing duration
   - return HTTP 202 after registering processing with `EdgeRuntime.waitUntil`
   - enforce an application deadline below the platform wall clock limit
   - dispatch by the trusted task kind
   - set the task run to `running` and increment `attempt_count`
   - log or echo the design prompt for now
   - archive the queue message and mark the run `completed` on success
   - set the run to `retrying` and leave the message in the queue after a transient failure
   - archive the message and mark the run `failed` after a permanent failure or the configured attempt limit
   - treat an already completed or failed run as a no op and archive its duplicate message

6. Add recovery invocation.

   Create a Supabase Cron job that invokes `ai-worker` every 30 seconds with the named automation secret read from Supabase Vault. The API fast path provides normal low latency. Cron provides recovery when an invocation is missed or a worker is terminated.

   The existing local `edge_runtime.policy = "per_worker"` setting must remain enabled so `EdgeRuntime.waitUntil` can finish during local tests.

## Scope Limits

- don’t generate nodes or edges yet
- don’t call any AI providers
- don’t update the canvas
- don’t expose Queue APIs or write access to browser roles
- don’t add a provider specific token endpoint or run token

## Check When Done

- The task run and queue message commit atomically.
- `POST /api/ai/design` returns a persisted run ID with HTTP 202.
- The fast path starts the worker without making queue durability depend on that invocation.
- Cron processes a queued message when the fast path is skipped.
- A failed delivery becomes visible again and stops after the configured attempt limit.
- An application deadline leaves enough time to persist retry state before platform shutdown.
- Project members can observe project run lifecycle through Realtime Postgres Changes, but cannot mutate it.
- Concurrent enqueue attempts for one project produce one active run and one HTTP 409 response.
- `supabase functions serve ai-worker` works locally with background processing.
- Database tests verify grants, RLS, constraints, queue retry behavior, and duplicate handling.
- `npm run build` passes.
